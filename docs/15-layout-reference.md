# Layout Reference — YBR Platform

> **⚠️ CRITICAL RULE FOR ALL FRONTEND AGENTS ⚠️**
>
> Every screen in this project has a **reference layout** generated by Stitch (design tool). These layouts contain:
>
> - A pixel-perfect **`screen.png`** — the visual target you must match exactly
> - A **`code.html`** — the reference HTML with Tailwind classes, color tokens, spacing, typography, and structure
>
> **Before implementing ANY page or component, you MUST:**
>
> 1. Read the `code.html` for that page as your primary implementation reference
> 2. View the `screen.png` to understand the visual target
> 3. Translate the HTML structure faithfully into React/Next.js components using the same Tailwind tokens
>
> **Never design from scratch. Never guess colors or spacing. Always follow the layout reference.**

## How to Use the Layout Reference

### Step 1 — Read the HTML First

Before writing a single line of React, open and read the `code.html` for the page. Extract:

```
✅ The exact Tailwind class names used
✅ The color token names (e.g., `bg-primary`, `text-on-surface-variant`)
✅ The component structure (what wraps what)
✅ The spacing tokens (e.g., `p-stack-lg`, `gap-stack-md`)
✅ The typography classes (e.g., `font-display-md text-display-md`)
✅ Any special CSS in the `<style>` tag (shadows, body gradients, etc.)
```

### Step 2 — Translate Structure to React

Convert the HTML structure into React JSX, preserving:

- All Tailwind classes exactly as written in the reference
- The same DOM hierarchy (nesting, flex/grid layouts)
- The same responsive patterns

### Step 3 — Replace Static Content with Dynamic Data

Replace hardcoded HTML values with props and data from hooks/server components, keeping all styling intact.

## Design System Tokens

> **Source of truth:** `ybr-plataform/platform/apps/web/src/app/globals.css`
> Always use Tailwind token class names — never hardcode hex values.

### Brand Tokens (runtime — set per creator)

```
/* These are injected by the server layout per creator. Use the token names, not hex. */
primary            → creator's brand color (e.g. bg-primary, text-primary, border-primary)
on-primary         → text color on primary backgrounds (e.g. text-on-primary)
primary-hover      → darker shade, auto-derived
primary-muted      → 10% opacity of primary on white — subtle hover bg
primary-container  → 6% opacity of primary on white — very subtle bg
```

### Base Neutrals (permanent — same for all creators)

```
background                → #fafaf9   (page background — warm stone)
surface                   → #ffffff   (cards, modals)
surface-container-lowest  → #ffffff
surface-container-low     → #f5f5f4   (input backgrounds)
surface-container         → #e7e5e4   (section backgrounds)
surface-container-high    → #d6d3d1   (dividers)
on-surface                → #1c1917   (primary text)
on-surface-variant        → #78716c   (secondary text, placeholders)
outline                   → #d6d3d1   (borders)
outline-variant           → #e7e5e4   (subtle borders)
```

### Semantic States

```
error             → #dc2626
error-container   → #fee2e2
success           → #16a34a
success-container → #dcfce7
```

## Critical UI Patterns (from Reference Layouts)

### Buttons — Primary Action

```html
<!-- Always rounded-full, min-height 48px, bg-primary -->
<button
  class="w-full h-12 bg-primary text-on-primary rounded-full font-button text-button
               hover:bg-surface-tint active:scale-95 transition-all shadow-md"
>
  Entrar
</button>
```

### Buttons — Secondary / Outline

```html
<!-- rounded-full, border, no fill -->
<button
  class="w-full h-12 border border-outline-variant bg-surface-container-lowest
               text-on-surface-variant rounded-full font-button text-button
               hover:bg-surface-container-low active:scale-95 transition-all
               flex items-center justify-center gap-2"
>
  Entrar com Google
</button>
```

### Form Inputs

```html
<!-- h-12, rounded-lg, border-outline-variant, focus ring primary -->
<input
  class="w-full h-12 px-stack-md rounded-lg border border-outline-variant
```

## Common Mistakes to Avoid

| ❌ Wrong                                    | ✅ Correct                                                                  |
| ------------------------------------------- | --------------------------------------------------------------------------- |
| `style={{ color: 'var(--color-primary)' }}` | `text-primary` (Tailwind token)                                             |
| `className="text-[#984207]"`                | `className="text-primary"`                                                  |
| `rounded-md`                                | `rounded-xl` for cards, `rounded-full` for buttons, `rounded-lg` for inputs |
| `bg-white`                                  | `bg-surface` (cards) or `bg-background` (page)                              |
| `font-bold text-2xl`                        | `font-display-md text-display-md` (design system scale)                     |
| Inline `box-shadow` with color tint         | `shadow-card` or `shadow-card-hover`                                        |
| `text-gray-500`                             | `text-on-surface-variant`                                                   |
| `border-gray-200`                           | `border-outline-variant`                                                    |
| Hardcoded hex like `bg-[#984207]`           | `bg-primary`                                                                |
| `bg-orange-700`, `bg-amber-500`             | `bg-primary` (creator-set, unknown at build time)                           |

## Workflow for Implementing a Page

```
1. FIND    → Locate the page in the mapping table above
2. READ    → Open and fully read the code.html for both desktop and mobile variants
3. PLAN    → Identify: layout structure, components needed, data sources
4. BUILD   → Translate HTML to React preserving ALL Tailwind classes
5. VERIFY  → Compare visually against screen.png — must match
```

**Reference files to open for each new page:**

```
# Login page example:

layout/desktop-layout/login_desktop/screen.png   ← Desktop visual

```

## Notes on Layout-Only Screens

Some mobile layouts have **no desktop counterpart** (auth flows are mobile-first). For these:

- Implement the mobile design as the single responsive design
- Scale up naturally for larger screens using responsive Tailwind prefixes (`md:`, `lg:`)
- Auth pages are centered cards — they work well at all sizes with `max-w-[480px]`

Some desktop layouts have **no mobile counterpart** (admin panel). For these:

- Implement the desktop design first
- Make it responsive by stacking columns on mobile (`flex-col md:flex-row`)
